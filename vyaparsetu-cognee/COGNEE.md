# Cognee Benchmark & Production Readiness Report: Paytm VyaparSetu

## Executive Verdict

Cognee proves effective as a semantic knowledge graph for multi-hop entity exploration, unstructured supplier rate comparisons, and grounded conversational Q&A. However, it is unsuitable as an atomic transactional ledger or a synchronous backend database.

In the Paytm VyaparSetu architecture, Cognee functions as an **asynchronous intelligence and audit layer**, while FastAPI backed by a relational/cache layer handles real-time counter transactions, mathematical aggregations, and UI latency guarantees.

---

## Where Cognee is Strong (Strengths & Proven Capabilities)

### 1. Zero-Friction Multi-Hop Rate Auditing

* Traces supplier invoices across successive deliveries without rigid schema migrations.
* Successfully tracked rate hikes on identical SKUs across dates (`2026-09-01` at ₹27.0 vs. `2026-09-16` at ₹28.5) and calculated the delta (+₹1.5) cleanly during Phase 4 testing.
* Eliminates the need for brittle SQL join chains when merchants query supplier pricing behavior across weeks.

### 2. Semantic Disambiguation of Kirana Vocabulary

* Resolves diverse colloquial phrasing into unified graph context when fed structured extraction payloads.
* Connects entities (`Distributor`, `Invoice`, `LineItem`, `Customer`, `Transaction`) into traversable relationship clusters (`supplied_by`, `owes`, `contains`).

### 3. Grounded, Natural Conversational Answers

* Successfully answered complex, composite merchant queries:
* *"What was the UPI collection total, supplier payout total, and net balance on 2026-09-16?"*
* Returned exact figures (₹6,200 collection, ₹3,850 payout, ₹2,350 net balance) directly from indexed settlement summaries without arithmetic distortion.



### 4. Deterministic Graph Topology via Structured JSON

* Ingesting standardized JSON dictionaries with explicit keys (`merchant_id`, `customer_id`, `event_type`) generated identical graph nodes across isolated test runs (`phase2_run_a` and `phase2_run_b`), avoiding the random entity types generated by raw prose.

---

## Where Cognee is Weak (Failure Modes & System Bottlenecks)

### 1. Prohibitive Retrieval & Search Latency

* Across 10 sequential load tests in Phase 6, `cognee.search()` averaged **51.30 seconds** per query (total turnaround ~57.70s).
* This makes synchronous invocation on the critical path of a merchant UI impossible; blocking a shopkeeper at the counter for ~50 seconds to confirm a credit entry fails user experience standards.

### 2. Stale Reads Under Consecutive Writes (Queue Inconsistency)

* High-frequency sequential writes triggered eventual consistency lag.
* By Run 10 of Phase 6, an immediate search returned a stale balance of **₹450.0** instead of the expected **₹500.0**, indicating background indexing queue saturation.

### 3. Lack of Native Idempotency and Deduplication

* `cognee.add()` appends new text chunks to the dataset without performing deduplication.
* Re-running an identical transaction script duplicates documents and entities, leading the RAG summarizer to inflate customer debt by aggregating duplicate records.

### 4. Brittle Entity Resolution on Fuzzy Keys

* In Phase 3, logging a customer as `"Suresh"` (`c_suresh_01`) and subsequently as `"suresh"` (lowercase, no phone) caused Cognee to generate **two separate customer nodes** (`c_suresh_01` with ₹350 debt and `c_suresh_02_unknown` with ₹300 debt) rather than reconciling them.
* Identity resolution must be performed upstream in FastAPI before data reaches Cognee.

### 5. Cross-Merchant Data Contamination in Shared Graphs

* In Phase 5 Strategy 1, seeding two merchants in one dataset caused both merchants to connect via shared date nodes (`2026-09-16`), producing an entangled graph cluster.
* Absolute data isolation requires spinning up dedicated datasets per merchant (`phase5_merchant_<id>`) rather than relying on LLM-prompted filtering.

## Final Architectural Rules for VyaparSetu

* **Ledger Accounting:** Maintain running balances, daily totals, and atomic credit updates inside a relational store (SQLite/PostgreSQL) via FastAPI. Math operations must remain deterministic and instantaneous (<50ms).
* **Asynchronous Cognee Sync:** Push confirmed JSON events to Cognee inside a background task worker. Never block the merchant's confirmation soundbox or UI on Cognee.
* **Isolated Datasets per Merchant:** Partition datasets strictly by merchant ID to eliminate cross-store relationship bridging.
* **Cognee's Dedicated Role:** Reserve Cognee for challan invoice rate audit alerts, fuzzy catalog reconciliation, and conversational summary insights.
